# SQL Analytics Workbench

Вебзастосунок для аналізу й вимірювання поведінки SQL-запитів у PostgreSQL:
виконання, розбір плану виконання, бенчмарк продуктивності та контрольовані
експерименти з індексами — на двох базах даних із різним характером даних.

Проєктно-технологічна практика, НУ «Львівська політехніка», кафедра АСУ.
Тема: «Аналіз та обробка даних у реляційних базах даних».

---

## 1. Проблематика

SQL часто сприймають як «чорну скриньку»: написав запит, отримав результат,
і на цьому все. Але той самий результат майже завжди можна отримати кількома
різними формулюваннями запиту — через `JOIN` чи через підзапит, через
`EXISTS` чи через `LEFT JOIN ... IS NULL`, з індексом чи без нього — і
PostgreSQL виконає їх **по-різному**, з різним планом виконання і різним
реальним часом. Студент чи розробник рідко бачить цю різницю, бо для цього
потрібно окремо запускати `EXPLAIN ANALYZE`, окремо мірити час, окремо
порівнювати — і робити це послідовно, за єдиною методикою, щоб цифри взагалі
можна було зіставляти між собою.

Ця система — інструмент саме для цього: дає змогу взяти конкретне бізнес-
питання («які клієнти витратили найбільше», «яка виручка за категорією
з проміжними підсумками»), побачити його SQL-формулювання, виконати,
розібрати план виконання по вузлах, виміряти реальний час серією прогонів
за фіксованою методикою — і порівняти з альтернативним формулюванням того
самого результату або з тим самим запитом до й після додавання індексу.
Другий шар проблематики — безпека: система дає користувачу писати й
виконувати **довільний** SQL, а не лише готові запити з каталогу, і має
робити це так, щоб довільний текст фізично не міг нічого змінити чи
зламати базу.

## 2. Що робить система

- **Каталог запитів** — 67 SQL-запитів (34 на `museum`, 33 на `dvdrental`),
  кожен описаний YAML-файлом: бізнес-питання українською, сам SQL, перелік
  задіяних можливостей мови (для звіту про покриття), і для 6 запитів —
  альтернативне формулювання (`variants`) того самого результату для
  порівняння планів.
- **Виконання** (`Виконати`) — запускає SQL у транзакції `READ ONLY` і
  повертає таблицю результату + пропоновану діаграму.
- **План виконання** (`План`) — `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`,
  розібраний у дерево вузлів з реальним і оціненим часом та позначкою
  вузлів, де оцінка планувальника розходиться з фактом більш ніж у 10 разів.
- **Бенчмарк** (`Бенчмарк`) — серія прогонів за фіксованою методикою
  (перший прогін — «холодний», не враховується; медіана — основний
  показник, плюс min/mean/p95/stddev), з блоком параметрів сервера,
  без яких цифри неможливо інтерпретувати.
- **Довільний SQL** — те саме виконання/план/бенчмарк, але на SQL-тексті,
  який вводить сам користувач, під захистом (розділ 6).
- **Експерименти з індексами** — керований сценарій «немає індексу → бенчмарк
  → створити індекс → бенчмарк знову → розмір індексу → прибрати або
  лишити»: 5 індексних експериментів на `museum` і порівняння звичайного
  `VIEW` з `MATERIALIZED VIEW`.
- **Структура БД** — таблиці, стовпці, індекси, обмеження обох баз.
- Усі вимірювання автоматично накопичуються в `reports/*.csv` — готові дані
  для звіту з практики, які ніхто не редагує вручну.

## 3. Технологічний стек і чому саме він

Стек фіксований свідомо: предмет дослідження цього проєкту — сам текст
SQL-запиту і план його виконання, тому нічого не повинно приховувати чи
генерувати SQL за студента.

**Backend — Python**
| Бібліотека | Навіщо саме вона |
|---|---|
| **FastAPI** | Асинхронний вебфреймворк з автоматичною валідацією запитів через Pydantic-моделі й готовим `/docs` (Swagger) без додаткового опису API вручну. |
| **uvicorn** | ASGI-сервер, яким FastAPI і запускається. |
| **psycopg 3** (`psycopg[binary,pool]`) | Драйвер PostgreSQL з нативною підтримкою `async`/`await` і вбудованим пулом з'єднань (`psycopg_pool`) — саме він забезпечує `BEGIN READ ONLY`, `statement_timeout` і безпечну параметризацію запитів. |
| **Pydantic v2** | Опис і валідація схеми YAML-каталогу запитів і всіх тіл запитів/відповідей API. |
| **pydantic-settings** | Конфігурація застосунку зчитується виключно з оточення (змінні `.env`), без жодного значення, захардкодженого в коді. |
| **PyYAML** | Розбір YAML-файлів каталогу запитів і експериментів. |
| **pytest / pytest-asyncio** | Тестовий фреймворк; `-asyncio` — бо більшість тестів звертаються до реальної бази через `async`-з'єднання. |
| **ruff** | Лінтер і форматер (заміна flake8 + black одним швидким інструментом). |

**База даних**
- **PostgreSQL 16** — усі вимірювання плану й продуктивності мають сенс лише
  для конкретної версії з конкретними параметрами (`shared_buffers`,
  `work_mem`, `random_page_cost` — усі явно задані в `docker-compose.yml`,
  а не успадковані з дефолтів образу).

**Frontend**
- **Чистий HTML/CSS/vanilla JavaScript (ES-модулі), без React, без Node.js,
  без npm, без збирача.** Chart.js підключається прямим `<script>` з CDN.
  Причина: фронтенд не є предметом дослідження цієї роботи і не повинен
  відволікати час і код-базу від того, що досліджується — SQL і план
  виконання.

**Свідомо не використано:** ORM (SQLAlchemy тощо) — бо ORM генерує SQL сам і
приховує його від дослідника, а порівнювати формулювання запитів, яких не
бачиш, неможливо; Alembic — схема веде окремий, керований вручну набір
`.sql`-файлів, які самі є частиною звіту; Redis/Celery — синхронна,
послідовна методика вимірювання (розділ 5) навмисно не потребує черг чи
кешу поза самим PostgreSQL.

## 4. Архітектурні рішення

- **Чотири пули з'єднань, а не одне.** На кожну з двох баз (`museum`,
  `dvdrental`) — окремий пул під роллю `saw_readonly` (лише `SELECT`,
  для всього, що бачить користувач) і окремий пул під роллю `saw_admin`
  (лише для команд із файлів `experiments/*.yaml` — DDL для індексних
  експериментів). Роль `saw_admin` ніколи не отримує SQL від клієнта.
- **Довільний SQL перевіряється двічі.** Спершу — застосунком: власний
  токенізатор (`app/security.py`) визначає межі операторів коректно навіть
  якщо крапка з комою стоїть усередині рядкового літералу, і відхиляє все,
  крім `SELECT`/`WITH`/`TABLE`/`VALUES`/`EXPLAIN` над ними. Потім — самою
  базою: усе виконується в транзакції з `SET TRANSACTION READ ONLY` під
  роллю, якій на рівні СУБД надано лише `GRANT SELECT`. Друга перевірка —
  та, що справді убезпечує дані, перша — щоб очевидно неправильний запит не
  доходив до бази взагалі.
- **Каталог запитів — дані, а не код.** Кожен запит — окремий YAML-файл;
  застосунок валідує весь каталог одним проходом під час старту і
  відмовляється запускатися з незрозумілою помилкою, якщо файл зіпсовано,
  замість випадкової відмови під час першого запиту користувача.
- **Методика бенчмарку зафіксована в одному місці** (`app/benchmark.py`) і
  свідомо не змінюється по ходу проєкту — інакше цифри з різних розділів
  звіту стають непорівнюваними між собою.
- **Розбір плану виконання за self time, не за cumulative time.**
  «Actual Total Time» вузла в `EXPLAIN` включає час усіх його дочірніх
  вузлів, тож найповільнішим за цим показником завжди виявляється корінь
  дерева. `app/explain.py` віднімає час дітей і враховує кількість `loops`,
  щоб «найповільніший вузол» справді вказував на вузьке місце запиту.
- **Кожен запит каталогу й кожен варіант перевірено виконанням проти
  реальних даних**, а не написано «на око» — це наскрізна вимога всього
  проєкту, і саме тому вона ж перевіряється автоматично: `make verify`
  реально виконує всі 67 запитів і всі варіанти щоразу.

## 6. Безпека

- Довільний SQL від користувача виконується **тільки** через пул `readonly`
  (роль `saw_readonly`, якій на рівні PostgreSQL надано лише
  `GRANT SELECT`), **тільки** в транзакції з `SET TRANSACTION READ ONLY`,
  **тільки** зі встановленим `SET LOCAL statement_timeout` (типово 15 с,
  див. `.env`).
- Пул `admin` використовується виключно для команд з файлів
  `experiments/*.yaml`. Клієнт передає лише `experiment_id` — жодного SQL чи
  імені об'єкта від клієнта до цього пула не доходить.
- Параметри запитів підставляються лише через параметризацію psycopg —
  ніде немає f-рядків чи `%`-форматування з користувацькими даними всередині
  SQL-тексту.
- Будь-яка помилка PostgreSQL повертається клієнту структуровано
  (`sqlstate`, повідомлення, позиція в тексті запиту) — ніяких голих 500 із
  Python-трасуванням у браузер.
- Секрети — лише в `.env` (не в git). У репозиторій потрапляє тільки
  `.env.example` із порожніми значеннями.

## 7. Конфігурація

Уся конфігурація — у файлі `.env` (створюється копією `cp .env.example .env`
і заповнюється власноруч; сам `.env` у git не потрапляє — лише шаблон).
`docker-compose.yml` читає ці змінні й передає їх у контейнери; жодне
значення не захардкоджено ні в `docker-compose.yml`, ні в коді Python.

| Група | Змінні | Що означають |
|---|---|---|
| Суперкористувач Postgres | `POSTGRES_SUPERUSER`, `POSTGRES_SUPERUSER_PASSWORD`, `POSTGRES_PORT` | Потрібні лише один раз — під час першого підняття контейнера, для створення баз і ролей нижче. Порт — той, на якому Postgres буде доступний із хоста (для pgAdmin, `psql` тощо). |
| Ролі застосунку | `SAW_ADMIN_USER/PASSWORD`, `SAW_READONLY_USER/PASSWORD` | Дві робочі ролі, якими застосунок узагалі ходить у базу (розділ 6). Паролі — будь-які, генеруються один раз під час `make up` і зберігаються тільки у вашому `.env`. |
| Ролі для людини | `MUSEUM_MANAGER_USER/PASSWORD` | SELECT-only роль для перегляду бази музейним менеджером вручну (через pgAdmin), застосунком не використовується. |
| Назви баз | `MUSEUM_DB`, `DVDRENTAL_DB` | Просто назви двох баз усередині одного контейнера Postgres. Змінювати нема потреби, якщо не хочете інших назв. |
| Параметри API | `API_PORT` | Порт, на якому інтерфейс/API доступні з хоста (типово 8000 → http://localhost:8000). |
| | `STATEMENT_TIMEOUT_MS` | Скільки мілісекунд PostgreSQL дозволяє виконуватися одному запиту, перш ніж примусово його перервати (типово 15000 = 15 с). Захист від запиту, що «зависне» назавжди. |
| | `DEFAULT_ROW_LIMIT` | Скільки рядків повертати клієнту за замовчуванням, якщо запит не задав ліміт явно (захист від випадкового вивантаження мільйонів рядків у браузер). |
| | `BENCHMARK_DEFAULT_RUNS` | Скільки разів запускати запит під час бенчмарку за замовчуванням (перший прогін — «холодний», не рахується, розділ 4). |
| | `LOG_LEVEL` | Рівень деталізації логів `uvicorn`/застосунку. |
| Права на `./reports` (лише Linux) | `HOST_UID`, `HOST_GID` | Контейнер `api` за замовчуванням пише файли від імені uid 10001 — на Linux-хості це майже ніколи не власник щойно клонованої `./reports`, тож бенчмарк і експерименти (вони пишуть файли) падають із `PermissionError`, хоча звичайне виконання запиту (воно нічого не пише) працює. Впишіть сюди власні значення з `id -u` і `id -g` — і контейнер писатиме від вашого імені. Можна лишити порожнім, якщо проблеми немає (типово на Docker Desktop для macOS/Windows). |
| pgAdmin (опційно) | `PGADMIN_EMAIL`, `PGADMIN_PASSWORD`, `PGADMIN_PORT` | Потрібні лише якщо піднімаєте `make tools` — веб-інтерфейс для ручного перегляду баз. |

## 9. dvdrental: дамп, типові проблеми при відновленні

Дамп не зберігається в репозиторії через розмір. Покласти файл у
`db/dvdrental/dvdrental.tar` і виконати `make reset`. Якщо файл відсутній,
стек усе одно підніметься, база `dvdrental` буде створена, але порожня —
про це повідомить лог контейнера `postgres`.

**Помилка при відновленні (`must be owner of extension plpgsql`).**
Публічний dvdrental.tar, що циркулює в туторіалах, створений ще
PostgreSQL 9.2 і містить записи `SCHEMA public` / `EXTENSION plpgsql`, які
неможливо відновити від імені непривілейованої ролі `saw_admin`.
`30_restore_dvdrental.sh` фільтрує ці п'ять службових TOC-записів через
`pg_restore --list`/`--use-list` перед відновленням — самих таблиць це не
торкається, лише записи схеми/розширення, які й так уже існують у щойно
створеній базі.

**`PermissionError` на `/api/benchmark` чи запуску експерименту.**
Це не проблема бази — див. `HOST_UID`/`HOST_GID` у розділі 7.

**Перевідновити лише dvdrental, не чіпаючи museum:**

```bash
make restore-dvd
make psql-dvd    # SELECT count(*) FROM rental;  -- має повернути 16044
```
