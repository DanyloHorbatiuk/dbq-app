# CLAUDE.md

Інструкції для Claude Code при роботі в цьому репозиторії.

## Контекст

Це навчально-дослідницький проєкт у межах проєктно-технологічної практики
(НУ «Львівська політехніка», спеціальність F3 «Комп'ютерні науки», 4 курс).
Тема: «Аналіз та обробка даних у реляційних базах даних».

Повне технічне завдання — у `SPEC.md`. **Перед виконанням будь-якого завдання прочитай
`SPEC.md`.** Якщо запит користувача суперечить ТЗ — скажи про це, не виконуй мовчки.

Результат роботи має двох «замовників»:

1. Працездатна система — вона має запускатися й працювати.
2. Захист перед комісією — код і рішення мають бути **пояснюваними**. Кожне нетривіальне
   рішення супроводжується коментарем «чому саме так», а не «що робить цей рядок».

Друге не менш важливе за перше. Красиве рішення, яке студентка не зможе пояснити на
захисті, є гіршим за просте й зрозуміле.

## Технологічний стек — фіксований

- PostgreSQL 16 (в Docker)
- Python 3.12, FastAPI, uvicorn, psycopg 3, Pydantic v2, PyYAML
- Фронтенд: статичні HTML/CSS/vanilla JS + Chart.js з CDN. **Без React, без збирачів,
  без npm.** Фронтенд не є предметом дослідження і не повинен займати час.
- pytest для тестів, ruff для лінтингу/форматування
- Docker Compose для розгортання

**Не пропонуй і не додавай:** ORM (SQLAlchemy, Tortoise), Alembic, Redis, Celery,
Node.js-тулчейн, TypeScript, Tailwind, будь-які фреймворки фронтенду. Якщо вважаєш,
що щось із цього справді потрібне — спочатку запитай і поясни, скільки часу це забере.

Причина відмови від ORM принципова: предметом дослідження є текст SQL-запиту і план
його виконання. ORM приховує згенерований SQL і робить порівняння формулювань
неможливим.

## Правила роботи

### Ітеративність

Не роби всю систему за один прохід. Працюй етапами з `ROADMAP.md`, після кожного етапу
зупиняйся і звітуй про зроблене. Один етап — одна логічна одиниця, яку можна перевірити.

### Перевіряй, а не припускай

- Після зміни SQL — запусти його в контейнері й покажи фактичний результат.
- Після зміни Python — запусти тести.
- Ніколи не пиши «має працювати». Або перевірено, або чесно сказано, що не перевірено.

### Обсяг файлів

Жоден Python-модуль не повинен перевищувати ~250 рядків. Якщо виходить більше —
це сигнал розділити відповідальність, а не привід зменшити відступи.

### SQL-запити каталогу

Кожен запит — окремий YAML-файл за схемою з розділу 3.3 `SPEC.md`. Вимоги до самого SQL:

- Ключові слова — ВЕЛИКИМИ літерами, `JOIN` з нового рядка, вирівняні відступи.
- Короткі змістовні псевдоніми таблиць (`p` для payment, `r` для rental).
- Повні імена з квіліфікацією схеми: `museum_network.tickets`, `public.payment`.
- **Ніякого хардкоду ідентифікаторів.** Потрібна конкретна виставка — шукай за назвою,
  потрібен працівник — за e-mail.
- Запит має бути виконуваним без правок після копіювання в pgAdmin.
- Коментар усередині SQL пояснює бізнес-логіку кроку, а не синтаксис.

Перед додаванням нового запиту перевір `GET /api/meta/coverage` — додавай насамперед ті,
що закривають ще не покриті можливості SQL, а не п'ятий варіант `GROUP BY`.

### Генерування даних

Генератор у `db/museum/07_generate_data.sql` має:

- починатися з `SELECT setseed(0.42);` — без цього дані не відтворювані, і всі
  вимірювання в звіті стають непорівнюваними між перезапусками;
- створювати **нерівномірні** розподіли (сезонність, «довгий хвіст»);
- працювати за розумний час: 300 тис. квитків мають генеруватися менш ніж за 60 с.
  Використовуй один `INSERT ... SELECT ... FROM generate_series`, а не цикл у PL/pgSQL;
- завершуватися `ANALYZE` по всіх заповнених таблицях — інакше планувальник працюватиме
  зі старою статистикою й перші вимірювання будуть хибними.

### Безпека — не обговорюється

Це пункт, за який на захисті питатимуть.

- Довільний SQL від користувача виконується **тільки** через пул `readonly`
  (роль `saw_readonly` з `GRANT SELECT`), **тільки** в транзакції `BEGIN READ ONLY`,
  **тільки** зі встановленим `SET LOCAL statement_timeout`.
- Пул `admin` використовується виключно для команд з файлів `experiments/*.yaml`.
  Клієнт передає `experiment_id`, а не SQL.
- Параметри запитів підставляються параметризацією psycopg. Жодного f-string
  або `%`-форматування з даними користувача в SQL.
- Імена об'єктів, якщо їх справді треба підставити динамічно — тільки через
  `psycopg.sql.Identifier`.
- Секрети — лише в `.env`. У репозиторій іде `.env.example` із пустими значеннями.

Якщо помітиш у моєму завданні щось, що порушує ці правила, — відмовся і поясни чому.

### Вимірювання продуктивності

Методика зашита в `app/benchmark.py` і має бути однаковою для всіх вимірювань:
N прогонів, перший фіксується окремо як «холодний» і не входить у статистику,
основний показник — медіана, додатково min/mean/p95/stddev. До кожного результату
додається блок `environment` (версія сервера, `shared_buffers`, `work_mem`,
`random_page_cost`, обсяги задіяних таблиць).

Не «покращуй» цю методику посеред роботи — інакше числа в різних розділах звіту
стануть непорівнюваними.

### Помилки

Будь-яка помилка PostgreSQL повертається клієнту структуровано: `sqlstate`, повідомлення,
позиція в тексті запиту. Ніяких голих 500 із трасуванням у браузер. Але й не ковтай
помилки мовчки — в лог вони мають потрапляти повністю.

## Команди

```
make up        # підняти все, розгорнути обидві бази
make down      # зупинити
make reset     # повністю перебудувати бази з нуля (видаляє том!)
make logs      # логи api
make psql-museum / make psql-dvd
make seed      # перегенерувати дані museum
make test      # pytest
make lint      # ruff check + ruff format --check
make verify    # перевірка критеріїв приймання з розд. 7 SPEC.md
make tools     # додатково підняти pgAdmin на :5050
```

## Чого не робити

- Не переписуй наявні файли цілком, якщо треба змінити частину — роби точкову правку
  і скажи, що саме змінив.
- Не змінюй структуру бази `dvdrental`. Можна лише додавати індекси в межах
  описаних експериментів.
- Не вигадуй числа. Якщо потрібен результат вимірювання — виміряй.
- Не додавай залежностей без потреби. Кожна нова бібліотека — це пункт, який
  доведеться пояснювати на захисті.
- Не пиши в `reports/` вручну — ці файли генеруються кодом.
