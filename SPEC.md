# ТЗ — SQL Analytics Workbench

Технічне завдання на розробку програмного забезпечення в межах проєктно-технологічної
практики. Тема індивідуального завдання: «Аналіз та обробка даних у реляційних базах даних».

---

## 1. Призначення та межі системи

### 1.1 Призначення

SQL Analytics Workbench (далі — Система) — навчально-дослідницький вебзастосунок для
інтерактивного виконання аналітичних SQL-запитів до двох баз даних PostgreSQL з
автоматичним вимірюванням часу виконання, розбором плану запиту та візуалізацією
результатів.

Система вирішує три задачі:

1. **Демонстраційну** — надає впорядкований каталог SQL-запитів, згрупованих за
   рівнями складності та задіяними можливостями мови, з поясненням бізнес-питання,
   на яке відповідає кожен запит.
2. **Дослідницьку** — дає змогу відтворювано вимірювати продуктивність запиту,
   порівнювати альтернативні формулювання одного запиту та досліджувати вплив
   індексів і матеріалізованих представлень.
3. **Звітну** — експортує результати виконання та серій вимірювань у формати,
   придатні для вставлення у звіт (CSV, PNG-діаграми, JSON-плани).

### 1.2 Що НЕ входить у межі

- Багатокористувацький режим, автентифікація, розмежування прав користувачів Системи.
- Редагування даних через інтерфейс (Система працює тільки на читання).
- Промислове розгортання, HTTPS, зовнішній доступ. Система розгортається локально.
- ORM і будь-яка абстракція над SQL — предметом дослідження є сам текст запиту.

### 1.3 Користувач

Єдиний тип користувача — аналітик/дослідник (студент і члени комісії під час захисту),
який має доступ до локального середовища.

## 2. Бази даних

Система працює з одним сервером PostgreSQL 16, на якому розгорнуто дві бази.

### 2.1 База `dvdrental` (існуюча, зовнішня)

Навчальна база прокату DVD (15 таблиць). Розгортається з файлу `db/dvdrental/dvdrental.tar`
командою `pg_restore`. **Структура цієї бази не змінюється.** Дозволено додавати лише
індекси в межах експериментів з продуктивності, і кожен такий індекс має бути описаний
у реєстрі експериментів (розд. 6.4).

### 2.2 База `museum` (власна розробка)

Схема `museum_network`. Базова версія схеми вже існує (8 таблиць, 3НФ) і наведена в
`db/museum/legacy_schema.sql` як довідка. У межах роботи схему потрібно **розширити**.

#### 2.2.1 Наявні таблиці (зберігаються)

| Таблиця | Призначення |
|---|---|
| `halls` | Зали музею (hall_id, name, floor) |
| `artifact_types` | Довідник типів експонатів |
| `exhibits` | Експонати |
| `staff` | Працівники |
| `exhibitions` | Виставки |
| `exhibition_items` | Зв'язка M2M «виставка — експонат» |
| `ticket_prices` | Тарифи |
| `tickets` | Продані квитки |

#### 2.2.2 Обов'язкові зміни наявних таблиць

| Об'єкт | Зміна | Обґрунтування |
|---|---|---|
| `exhibitions` | Прибрати `CHECK (start_date >= '2026-01-01')`, замінити на `CHECK (start_date >= DATE '2000-01-01')` | Наявне обмеження унеможливлює історичні дані та генерування вибірки за минулі роки |
| `artifact_types` | Додати `parent_type_id INT REFERENCES artifact_types(type_id)` | Ієрархія типів для рекурсивного CTE |
| `ticket_prices` | Додати `valid_from DATE NOT NULL`, `valid_to DATE`; зняти `UNIQUE(exhibition_id, visitor_type)`, замінити на `EXCLUDE`-обмеження за перетином періодів | Історія цін (SCD Type 2): без неї неможливо коректно порахувати виручку за минулі періоди |
| `tickets` | Додати `visit_date DATE`, `payment_method`, `sales_channel`, `quantity SMALLINT DEFAULT 1` | Сегментація продажів за каналами й способами оплати |
| `exhibits` | Додати `acquisition_date DATE`, `insurance_value NUMERIC(12,2)`, `condition_status` | ABC-аналіз колекції, аналіз вартості за залами |
| `exhibitions` | Додати `hall_id INT REFERENCES halls(hall_id)` | Потрібно для обмеження на перетин виставок в одному залі |

#### 2.2.3 Нові таблиці

| Таблиця | Склад | Призначення для аналітики |
|---|---|---|
| `visitor_feedback` | feedback_id, exhibition_id FK, rating SMALLINT CHECK 1..5, comment TEXT, created_at TIMESTAMPTZ | Агрегати, перцентилі, повнотекстовий пошук по коментарях (GIN-індекс) |
| `restorations` | restoration_id, exhibit_id FK, staff_id FK, start_date, end_date, cost NUMERIC | Витрати, завантаженість персоналу, запити з перетином періодів |
| `guided_tours` | tour_id, exhibition_id FK, staff_id FK, starts_at TIMESTAMPTZ, capacity SMALLINT | Аналіз заповнюваності, розкладу |
| `tour_bookings` | booking_id, tour_id FK, ticket_id FK, status | Друга M2M-зв'язка, конверсія бронювань |
| `audit_log` | log_id, table_name, operation, changed_at, changed_by, old_row JSONB, new_row JSONB | Демонстрація тригерів; джерело для запитів по JSONB |

#### 2.2.4 Обов'язкові обмеження цілісності

Не менше 10 обмежень, серед яких обов'язково:

- `EXCLUDE USING gist` на `exhibitions` — заборона перетину дат двох виставок в одному
  залі (потребує розширення `btree_gist`);
- `EXCLUDE` на `ticket_prices` — заборона перетину періодів дії тарифу для однієї пари
  (виставка, категорія відвідувача);
- перевірка формату e-mail (регулярний вираз) — вже є, зберегти;
- перевірка діапазону рейтингу у `visitor_feedback`;
- перевірка `end_date >= start_date` у всіх таблицях з періодами;
- перевірка невід'ємності всіх грошових полів.

#### 2.2.5 Програмні об'єкти

- Функції `update_staff_data()` і `sell_ticket()` — зберегти, адаптувати під нову
  структуру `ticket_prices` (пошук чинного тарифу на дату).
- Нова функція `museum_network.price_on_date(exhibition_id, visitor_type, on_date)` —
  повертає чинний тариф на задану дату.
- Тригерна функція `museum_network.fn_audit()` + тригери `AFTER INSERT OR UPDATE OR DELETE`
  на `tickets` і `ticket_prices`, що пишуть у `audit_log`.
- Представлення `v_quarterly_sales_performance` — зберегти.
- Матеріалізоване представлення `mv_monthly_revenue` — виручка за місяцями у розрізі
  виставки й категорії відвідувача, з унікальним індексом для `REFRESH CONCURRENTLY`.
- Ролі: `museum_manager` (SELECT-only) — зберегти; додати `saw_readonly` як роль,
  під якою працює Система.

#### 2.2.6 Вимоги до обсягу тестових даних

Генерування виконується засобами `generate_series` + `random()` з фіксованим `setseed()`
для відтворюваності.

| Таблиця | Мінімальний обсяг |
|---|---|
| `halls` | 20 |
| `artifact_types` | 40 (ієрархія на 3 рівні) |
| `exhibits` | 5 000 |
| `staff` | 200 |
| `exhibitions` | 400 (за період 2019–2026) |
| `exhibition_items` | 30 000 |
| `ticket_prices` | 4 000 (з історією періодів) |
| `tickets` | **не менше 300 000** |
| `visitor_feedback` | 80 000 |
| `guided_tours` | 8 000 |
| `tour_bookings` | 50 000 |
| `restorations` | 3 000 |

Розподіли мають бути **нерівномірними**: сезонність продажів по місяцях, «довгий хвіст»
популярності виставок, різна активність працівників. Рівномірний розподіл робить
аналітичні запити беззмістовними, а плани запитів — нереалістичними.

## 3. Каталог запитів

### 3.1 Кількісні вимоги

| База | Мінімум запитів |
|---|---|
| `dvdrental` | 30 |
| `museum` | 25 |

Не менше **6 пар** запитів-варіантів (той самий результат, різні формулювання) для
порівняння планів виконання.

### 3.2 Рівні складності

| Рівень | Зміст | Мінімум |
|---|---|---|
| 1 | `WHERE`, `ORDER BY`, `LIMIT`, `DISTINCT`, `CASE`, `COALESCE`, функції дати й рядків | 8 |
| 2 | Усі види `JOIN`, `GROUP BY`/`HAVING`, агрегати, `UNION`/`INTERSECT`/`EXCEPT`, скалярні та корельовані підзапити, `EXISTS`/`IN`/`ANY` | 18 |
| 3 | CTE, рекурсивні CTE, віконні функції, `LATERAL`, `GROUPING SETS`/`ROLLUP`/`CUBE`, `FILTER`, `percentile_cont`, `json_agg` | 20 |
| 4 | Комплексні сценарії: RFM-сегментація, когортний аналіз утримання, ABC-аналіз, top-N у групі, сезонність, виявлення аномалій | 9 |

Кожна можливість SQL зі списку має бути задіяна щонайменше в одному запиті. Система
повинна вміти показати покриття (розд. 5.6).

### 3.3 Формат опису запиту

Один запит — один YAML-файл у `queries/<database>/level<N>/<id>.yaml`.

```yaml
id: dvd-l3-04
database: dvdrental            # dvdrental | museum
level: 3                       # 1..4
title: "Накопичувальна частка виручки за категоріями фільмів"
business_question: >
  Які категорії фільмів формують 80 % сукупної виручки прокату?
sql_features: [cte, window_function, sum_over, order_by]
description: >
  Запит обчислює виручку за категоріями, накопичувальний підсумок і частку
  від загального обсягу. Демонструє заміну корельованого підзапиту віконною функцією.
expected_insight: >
  Розподіл має вигляд «довгого хвоста»: перші 6–7 категорій дають близько 80 % виручки.
chart:
  type: bar                    # bar | line | pie | scatter | none
  x: category_name
  y: [revenue]
  secondary_y: cumulative_share
parameters:                    # опційно, підставляються як %(name)s
  - name: min_revenue
    type: number
    default: 0
sql: |
  WITH category_revenue AS (
      SELECT c.name AS category_name,
             SUM(p.amount) AS revenue
      FROM public.payment p
      JOIN public.rental r   ON r.rental_id = p.rental_id
      ...
      GROUP BY c.name
  )
  SELECT ...
variants:                      # опційно — альтернативні формулювання
  - label: "через корельований підзапит"
    sql: |
      SELECT ...
```

Поля `id`, `database`, `level`, `title`, `business_question`, `sql_features`, `sql` —
обов'язкові. Система валідує файли каталогу на старті й відмовляється запускатися,
якщо є невалідний файл або дублікат `id`.

## 4. Архітектура

```
браузер (HTML + JS + Chart.js)
        │  HTTP/JSON
        ▼
FastAPI (uvicorn)
        │
        ├── catalog      — читання та валідація YAML-каталогу
        ├── executor     — виконання запиту в READ ONLY транзакції
        ├── explain      — EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) + розбір дерева
        ├── benchmark    — серія прогонів, агрегація статистики
        ├── experiments  — керовані експерименти з індексами
        └── export       — CSV / JSON
        │  psycopg 3
        ▼
PostgreSQL 16  ─── БД dvdrental
               └── БД museum
```

### 4.1 Підключення до БД

Система тримає **два незалежні пули з'єднань на кожну базу**:

| Пул | Роль | Призначення |
|---|---|---|
| `readonly` | `saw_readonly` (GRANT SELECT) | Усі запити з каталогу та довільний SQL користувача |
| `admin` | `saw_admin` (власник схеми) | Тільки експерименти з індексами та `REFRESH MATERIALIZED VIEW` |

Пул `admin` **ніколи** не використовується для виконання довільного SQL, введеного
користувачем. Це принципова вимога, а не рекомендація.

## 5. Функціональні вимоги

### ФВ-01. Каталог запитів

`GET /api/catalog?database=&level=&feature=&q=`

Повертає перелік запитів із метаданими (без тексту SQL). Підтримує фільтрацію за базою,
рівнем, задіяною можливістю SQL і повнотекстовий пошук по заголовку/питанню.

`GET /api/catalog/{query_id}` — повний опис, включно з текстом SQL і варіантами.

### ФВ-02. Виконання запиту

`POST /api/execute`

```jsonc
// запит
{
  "query_id": "dvd-l3-04",     // або "sql": "SELECT ..." + "database": "museum"
  "variant": null,              // індекс варіанта, якщо виконується альтернативне формулювання
  "parameters": { "min_revenue": 100 },
  "row_limit": 1000,
  "with_plan": true             // додати EXPLAIN ANALYZE
}
```

```jsonc
// відповідь
{
  "query_id": "dvd-l3-04",
  "columns": [{"name": "category_name", "type": "text"}, ...],
  "rows": [["Sports", 4892.19, 0.11], ...],
  "row_count": 16,
  "truncated": false,
  "timings": {
    "planning_ms": 0.412,
    "execution_ms": 38.774,
    "roundtrip_ms": 51.2
  },
  "buffers": {"shared_hit": 1842, "shared_read": 0},
  "plan": { /* дерево з EXPLAIN FORMAT JSON */ },
  "plan_summary": {
    "node_types": ["Sort", "HashAggregate", "Hash Join", "Seq Scan"],
    "slowest_node": {"type": "Hash Join", "actual_total_time": 31.2},
    "estimation_error": 1.8          // max(actual_rows/estimated_rows) по дереву
  }
}
```

Вимоги до реалізації:

- Виконання відбувається в транзакції, відкритій як `BEGIN READ ONLY`.
- Перед виконанням встановлюється `SET LOCAL statement_timeout = <з конфігурації>`.
- Параметри підставляються **тільки** через параметризацію psycopg, ніколи через
  форматування рядків.
- `roundtrip_ms` вимірюється на боці Python як повний час від відправлення до отримання
  всіх рядків; `planning_ms` і `execution_ms` беруться з `EXPLAIN`.
- Якщо рядків більше за `row_limit`, повертається зрізаний набір і `truncated: true`.

### ФВ-03. Довільний SQL

Те саме `POST /api/execute` з полем `sql`. Додатково до READ ONLY транзакції
застосовується перевірка на боці застосунку (ешелонований захист):

- відхиляти запит, що містить більше одного оператора (перевірка через розбір, не через
  наївний пошук `;` — крапка з комою може бути всередині рядкового літерала);
- відхиляти запит, що не починається з `SELECT`, `WITH`, `TABLE`, `VALUES` або `EXPLAIN`;
- відхиляти службові команди (`COPY ... TO PROGRAM`, `SET`, `\\copy`).

Кожна відмова повертає HTTP 400 із зрозумілим поясненням причини.

### ФВ-04. Аналіз плану виконання

`POST /api/explain`

```jsonc
{ "query_id": "...", "analyze": true, "buffers": true, "database": "museum" }
```

Повертає план у JSON і його розбір: плаский перелік вузлів із часом, кількістю рядків
(оцінка/факт), відношенням `loops`, і позначкою вузлів, де похибка оцінки перевищує
10-кратну. Фронтенд відображає це деревом із кольоровим маркуванням частки часу.

### ФВ-05. Серія вимірювань (benchmark)

`POST /api/benchmark`

```jsonc
{
  "query_id": "museum-l4-02",
  "runs": 10,
  "discard_first": true,
  "cold_cache": false
}
```

```jsonc
{
  "runs": 10,
  "cold_run_ms": 412.8,
  "stats": {
    "min_ms": 38.1, "median_ms": 39.4, "mean_ms": 41.0,
    "p95_ms": 48.7, "max_ms": 52.3, "stddev_ms": 3.9
  },
  "samples_ms": [38.1, 39.0, ...],
  "environment": {
    "server_version": "16.4",
    "shared_buffers": "256MB",
    "work_mem": "16MB",
    "random_page_cost": "1.1",
    "table_sizes": {"museum_network.tickets": "48 MB"}
  }
}
```

Методика зашита в код і має бути **однаковою для всіх вимірювань у звіті**: перший
прогін фіксується окремо як «холодний» і не входить у статистику; основним показником
є медіана. Блок `environment` обов'язковий — без нього числа в звіті неінтерпретовні.

### ФВ-06. Експерименти з індексами

`GET /api/experiments` — перелік заздалегідь описаних експериментів.
`POST /api/experiments/{experiment_id}/run`

Експеримент описується у файлі `experiments/*.yaml`:

```yaml
id: idx-museum-tickets-date
database: museum
title: "Індекс за датою продажу квитка"
query_id: museum-l2-07
index_name: idx_tickets_purchase_date
create_sql: CREATE INDEX idx_tickets_purchase_date ON museum_network.tickets (purchase_date);
```

Сценарій виконання:

1. Переконатися, що індексу немає (`DROP INDEX IF EXISTS`), виконати `ANALYZE`.
2. Прогнати benchmark → результат «без індексу», зберегти план.
3. Створити індекс, виконати `ANALYZE`.
4. Прогнати benchmark → результат «з індексом», зберегти план.
5. Повернути обидва набори, розмір індексу (`pg_relation_size`), час його створення
   та зміну типу вузла доступу в плані.
6. Стан бази повернути до початкового (індекс видалити), якщо у запиті
   `keep_index: false`.

**Обмеження безпеки:** виконуються тільки SQL-команди з файлів експериментів.
`index_name` і `create_sql` не приймаються від клієнта — клієнт передає лише
`experiment_id`.

### ФВ-07. VIEW проти MATERIALIZED VIEW

Окремий експеримент того ж механізму: benchmark запиту до `v_quarterly_sales_performance`
проти запиту до `mv_monthly_revenue`, з фіксацією часу `REFRESH MATERIALIZED VIEW`
і обсягу, який займає матеріалізоване представлення.

### ФВ-08. Статистика сервера

`GET /api/stats/top-queries?limit=20&order_by=total_exec_time` — вибірка з
`pg_stat_statements`.
`GET /api/stats/unused-indexes` — індекси з `idx_scan = 0` за даними `pg_stat_user_indexes`.
`GET /api/stats/table-sizes` — обсяги таблиць і індексів.
`POST /api/stats/reset` — `pg_stat_statements_reset()`.

### ФВ-09. Візуалізація

Фронтенд будує діаграму за підказкою `chart` з опису запиту. Якщо підказки немає,
застосовується евристика: перший текстовий стовпець — вісь X, числові — серії; для
результатів з одним числовим стовпцем і ≤10 рядками пропонується кругова діаграма.
Користувач може перемкнути тип діаграми та обрати стовпці вручну. Перемикач
«таблиця / діаграма / план запиту».

### ФВ-10. Експорт

- `GET /api/export/csv?...` — результат останнього виконання у CSV (UTF-8 з BOM, щоб
  коректно відкривався в Excel).
- Кнопка збереження діаграми у PNG на боці браузера.
- `POST /api/export/benchmark-report` — зведена таблиця всіх проведених вимірювань
  у CSV у каталог `reports/`, для перенесення у звіт.

### ФВ-11. Метадані

`GET /api/meta/server-info` — версія PostgreSQL, ключові параметри конфігурації.
`GET /api/meta/schema?database=museum` — перелік таблиць, стовпців, індексів, обмежень
(для сторінки «Структура БД»).
`GET /api/meta/coverage` — які можливості SQL із контрольного списку покриті запитами
каталогу і скількома. Потрібно для перевірки повноти перед здачею.

## 7. Критерії приймання

Робота вважається виконаною, коли одночасно справджується:

1. `git clone` → `cp .env.example .env` → `make up` дає працездатну систему на
   `http://localhost:8000` без ручних кроків.
2. `make verify` проходить без помилок і друкує звіт: кількість запитів у каталозі за
   рівнями, покриття можливостей SQL, обсяги таблиць, кількість тестів.
3. У `museum_network.tickets` не менше 300 000 рядків; усі таблиці з розд. 2.2.6
   заповнені до вказаних обсягів.
4. Каталог містить не менше 55 запитів, з них не менше 20 третього рівня.
5. Кожен запит каталогу успішно виконується (перевіряється автотестом, що прогонює
   весь каталог).
6. Щонайменше 5 експериментів з індексами дають виміряну різницю та зміну типу вузла
   доступу в плані.
7. Експорт `reports/benchmarks.csv` містить усі проведені вимірювання у форматі,
   придатному для прямого вставлення у звіт.

## 8. Матеріали для звіту

Система має згенерувати (у каталог `reports/`) без ручної обробки:

- `benchmarks.csv` — усі вимірювання: запит, рівень, холодний прогін, min/median/mean/p95,
  оточення;
- `index_experiments.csv` — результати експериментів з індексами: до/після, розмір індексу,
  тип вузла доступу;
- `catalog_coverage.csv` — покриття можливостей SQL;
- `table_sizes.csv` — обсяги таблиць і індексів обох баз;
- `plans/*.json` — збережені плани виконання для запитів, згаданих у звіті.
