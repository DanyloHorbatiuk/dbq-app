## dvdrental: наповнення каталогу — ЗАКРИТО

Було відкладено на Етапі 10 через відсутність `db/dvdrental/dvdrental.tar` у
середовищі розробки (деталі — в історії git цього файлу). Закрито:

- Дамп отримано, відновлення виправлено: публічний dvdrental.tar створений
  ще PostgreSQL 9.2 і містить записи `SCHEMA public` / `EXTENSION plpgsql`,
  які не вдається відновити від імені непривілейованої ролі `saw_admin`.
  `docker/postgres/initdb/30_restore_dvdrental.sh` тепер фільтрує ці п'ять
  TOC-записів через `pg_restore --list` / `--use-list` перед відновленням,
  замість того щоб падати посеред `docker-entrypoint-initdb.d` і залишати
  `40_init_museum.sh`/`50_grants.sh` невиконаними.
- Права на запис у `reports/` для контейнера api виправлено через
  `user: "${HOST_UID:-10001}:${HOST_GID:-10001}"` у `docker-compose.yml`
  (див. `.env.example`) — бенчмарк і експерименти пишуть файли, звичайне
  виконання запиту — ні, тому симптом проявлявся вибірково.
- `make restore-dvd` — перевідновити лише dvdrental, не чіпаючи museum.
- Каталог `queries/dvdrental/` наповнено: 33 запити (8/9/12/4 за рівнями),
  усі перевірені виконанням проти реальних даних.
- `tests/test_catalog_runs.py` тепер обирає пул за `entry.database`
  замість жорсткої прив'язки до museum.
- `make verify` (SPEC.md §7) проходить повністю: 67 запитів у каталозі,
  21 запит 3-го рівня, 100% покриття SQL, усі запити виконуються,
  5/5 індексних експериментів дають зміну вузла доступу.

Індексні експерименти на dvdrental свідомо не додавались — обсяг даних там
(~16 тис. рядків) замалий, щоб різниця до/після індексу була вимірювано
значущою, а критерій §7.6 (≥5 експериментів) уже закритий на museum.
